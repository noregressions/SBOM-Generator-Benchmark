# Tool comparison: every axis, one row per generator

Generated by `compare-tools.py` from the outputs of the three runs in this repo. Re-run those first if you change a tool version (`./run-all.sh`, `./scope-runs/run.sh`, `./evaluate`). `./evaluate` rebuilds this file; after the other two, run `python3 compare-tools.py`.

The three runs measure different things and the columns keep them apart:

- **Shape** (sbomqs on one representative sample-app SBOM per tool, and the mean sbomqs scores over every document the tool produced in the criteria run): does the document have the fields a baseline asks for. Says nothing about whether the inventory is right.
- **Truth** (criteria run against `testcases/`, ground truth in `testcases/<name>/expected.json`): did the tool name what actually ships, at the right version, under the right purl, without passing off test/dev/build tooling as shipped, with correct hashes.
- **Hidden** (same run): of the components that only exist because of shading, bundling, Maven plugin realms, BOM imports, npm `prepack` or PEP 517 backends, how many did the tool name at any stage it ran.
- **Scope** (scope-runs on sample-app): can the tool emit a runtime-only SBOM, did known test packages leak into it, and are dev packages in the combined SBOM labelled so a consumer can filter them.

Columns are blank where a tool was not part of a run. Full tables: [`criteria/SCORECARD.md`](criteria/SCORECARD.md), [`scope-runs/RESULTS.md`](scope-runs/RESULTS.md), [`tools/sbomqs/output/scores.txt`](tools/sbomqs/output/scores.txt).

## Reading the table

- Shape and truth are independent axes. As published, the highest-recall tools (SBOM+ 1.0.0, sbom-tool) had the lowest conformance because they emitted no hashes, licences or suppliers; the SBOM+ re-run with those fields added scores 9.9 on NTIA/CISA 2026 with the same inventory. The best-conforming scanner documents (cyclonedx-maven-plugin, Trivy on an unzipped artefact) still miss whole categories of content.
- Recall at image stage is low for everyone except the image-native tools, and near zero for cdxgen, because the Spring Boot jar is not opened.
- Only the build plugins see the plugin realm; only the source-stage tools see bundled npm packages; nothing sees a shaded library once its leftover `pom.properties` is gone. Those three facts are the argument for recording at build time rather than scanning afterwards (see [`criteria/README.md`](criteria/README.md)).
