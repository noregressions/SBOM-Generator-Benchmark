Methodology

What is measured, how the right answer was established, how the numbers are counted, and what they cannot tell you.

The two scores

Content accuracy asks whether a document is true: does it name what actually ships, at the right version, without passing off test, dev or build tooling as shipped, and with correct hashes? It is measured against each test case's ground truth.

Baseline conformance asks whether a document is complete: does it carry the fields the published baselines want? It is measured by sbomqs, which scores a document out of 10 against NTIA 2021, the NTIA/CISA 2026 revision, BSI TR-03183-2 v2.1 and FSCT v3. CycloneDX documents are also checked against their schema with cyclonedx-cli.

The two are kept apart everywhere on this site, because they disagree.

A third view asks what the first two are for. The security view looks every component of every SBOM up in a vulnerability database and checks whether the SBOM would raise the advisories that apply to what ships, and only those.

Ground truth

Each test case has an expected.json, written by hand from the project's build files, its lockfiles and the listing of the built archive. Each test case also has a proof-check.sh that asserts what ends up in the artefact. It records what the build produced, not what any SBOM tool reported.

It keeps three kinds of component apart:

  • Shipped: present in the artefact. This includes components that were transformed on the way in: a library relocated into another jar by shading, or compiled into a JavaScript bundle. They still ship, even though no package boundary survives.
  • Not shipped: test and dev dependencies, provided-scope APIs, build plugins and their payloads, and imported BOMs. They influence the build, or run during it, and are not in the artefact.
  • Hidden: a tag on either kind, naming the mechanism that keeps the component out of an ordinary dependency list.

A tool may list something that does not ship, provided it marks it. A component with a scope of excluded or optional, or a property saying it is dev or test, counts as labelled. Without such a mark it counts as leaked.

The three stages

Every test case is scanned at up to three stages: source (the checkout, without build outputs or caches), artefact (the built jar, WAR, package or environment) and image (the container). Scanners get a copy of the source tree with build outputs removed, so that the source stage means the checkout and not the checkout plus everything the build produced. Tools that have to run the build use the real tree.

How the counts are made

The scorer reads CycloneDX and SPDX JSON, keeps package components, and reduces each to a package URL without qualifiers. It compares them with the ground truth, restricted to the test case's ecosystems.

Shipped found
Components that really ship and that the tool named at the exact version, out of all that ship.
Wrong ver
Components the tool named, but at a version that does not ship.
Wrong purl
Components named with the right name and version but under the wrong group or namespace, so no vulnerability database will match them. Lower is better.
Leaked
Things that do not ship (test, dev and build tooling, provided-scope and BOM imports) listed as if they did, with nothing a consumer could filter on. Lower is better.
Labelled
Things that do not ship, listed with a scope or property that marks them as such. This is the correct way to include them, so a high number is not a fault.
Hashes ok
Hashes the tool emitted that match the real digest of the jar inside the built artefact, out of the hashes it emitted for those jars.
In scope
Components whose package type is one of the test case's ecosystems. Operating-system packages in images are left out.

Denominators. Shipped found is always out of the full list of shipped components for that test case, at every stage. On the results page a tool's total adds up the test cases it ran on, so two tools' totals can have different denominators; the Cases column says how many. No figure on this site averages a tool across stages.

What this cannot tell you

  • It is small. 6 test cases in 4 ecosystems (Go, Maven, npm and pip). There is no Gradle, Rust or .NET test case.
  • The test cases are adversarial. Each was built to expose one hiding mechanism. They are not a sample of typical projects, and a tool's result here does not predict its result on yours.
  • It does not name a best tool. A tool can be strong at one stage and deliberately not target another.
  • One configuration per tool. Each tool is run one way, with the command in its adapter. A different or tuned configuration may do better.
  • One run. The published numbers come from a single run. cdxgen's result on a Spring Boot jar has differed by one or two components between identical runs, because its guess at the Maven group of some jars changes.
  • Found does not say why. A hidden component counts as found when its package URL matches, even when the tool found it for an incidental reason, such as a metadata file the shade plugin left behind.
  • Conformance is one tool's reading. The baseline scores are sbomqs' interpretation of each baseline, not a certificate.
  • The security view is a lookup, not an assessment. It asks which advisories a database returns for the components an SBOM names. It does not say whether the vulnerable code is reachable, and it depends on Grype's data on the day of the run.
  • The ground truth is hand-written. It can be wrong. If you find an error, open an issue.
  • Platform. This run was made on aarch64 Linux. Some npm packages are platform-specific, so the dev-dependency lists differ on other platforms.

Who made this

Disclosure. The author of this benchmark also develops SBOM+ (sbom-plus-maven-plugin), one of the tools measured, and most of the test cases come from the same author's workshop on hidden dependencies. Read SBOM+'s results with that in mind. Every generated SBOM, the ground truth and the scoring code are in the repository, so any result can be checked. Maintainers of the tools measured here are invited to reproduce the run and to challenge a result or a test case by opening an issue.

Run it yourself

You need Docker, make and git. The first run builds the tool image, which takes a few minutes and about 4 GB.

git clone https://github.com/noregressions/SBOM-Generator-Benchmark.git
cd SBOM-Generator-Benchmark
make            # build the test cases, run every tool, score, rebuild this site
make clean      # remove what the build left behind

A full run takes roughly ten minutes and ends with Failed steps: none. The scores land in criteria/output/scores.json and the generated SBOMs beside them, under criteria/output/<test case>/<stage>/.

To point the same tools at your own project:

make scan TREE=/path/to/your/project

That writes a report and every generated SBOM into sbom-report/ in your project. Your project has no ground truth, so the report cannot say which tool is right. It shows where the tools disagree, which is where to look first. A disagreement is a reason to investigate, not proof that either tool is wrong.
