The two scores

Every document a tool produces gets two scores, and every table on this site keeps them in separate, labelled groups of columns.

Content accuracy asks whether the document is true: does it name what actually ships, at the right version, without passing off test, dev or build tooling as shipped, and with correct hashes? It is measured against each test case's ground truth.

Baseline conformance asks whether the document is complete: does it carry the fields the published baselines (NTIA, NTIA/CISA, BSI) want? It is measured by the sbomqs tool, out of 10.

The two disagree, and the disagreement is the point. A document can score 10 for baseline conformance while listing a hundred components that never ship.

Mean recall
Of the components that really ship, the share the tool named at the exact version, averaged over its documents. Higher is better.
Wrong purl
Components named with the right name and version but under the wrong group or namespace, so no vulnerability database will match them. Lower is better.
Leaked
Things that do not ship (test, dev and build tooling, provided-scope and BOM imports) listed as if they did, with nothing a consumer could filter on. Lower is better.
Labelled
Things that do not ship, listed with a scope or property that marks them as such. This is the correct way to include them, so a high number is not a fault.
sbomqs quality
sbomqs' overall quality score for the document, 0 to 10. It measures how complete the fields are, not whether the inventory is right.
NTIA 2021
Score out of 10 against the NTIA minimum elements for an SBOM (2021): supplier, name, version, identifiers, dependencies, author, timestamp.
NTIA/CISA 2026
Score out of 10 against the 2026 NTIA/CISA revision of the minimum elements, which adds hashes, licences and more.
BSI v2.1
Score out of 10 against the German BSI technical guideline TR-03183-2 version 2.1, which asks for more per component than the NTIA lists do.

Tools run at different stages and on different test cases, so this table is a summary, not a ranking: a build plugin that only sees source is not competing with a scanner that also reads images. Follow a tool's link for every document it produced.

The three stages

Every test case is scanned at up to three stages: source (the checkout, without build outputs or caches), artefact (the built jar, WAR, package or environment) and image (the container). The hidden mechanisms show up as differences between stages, which is why one scan is never enough.
