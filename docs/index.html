Does your SBOM describe what you actually shipped?

A well-formed SBOM is not necessarily a complete or accurate account of the software shipped.

The SBOM Generator Index runs 13 free SBOM generators against 6 small projects built to hide a dependency in a specific, documented way. For each project we know what ends up in the shipped artefact, so every SBOM can be checked against it. Each document gets two scores: content accuracy (is it true?) and baseline conformance (does it have the fields the published baselines ask for?).

What the run shows

Four findings, each with the measurement behind it. Observed is what this run recorded. Likely reason is our reading of why, which the data supports but does not prove.

Conformance is not completeness

Observed On spring-node at the source stage, sbom-tool 4.1.13 scored 10.0 out of 10 against the NTIA 2021 minimum elements. The same document lists 86 components that do not ship, with nothing to tell a consumer so, and names 39 of the 40 that do.

Likely reason The baseline checks that every component has a supplier, a name, a version and an identifier. It does not ask whether the component belongs in the list, and a test or build-time dependency carries those fields as readily as a runtime one.

What it costs Anyone matching this document against vulnerability data will chase advisories for code that was never deployed, and has no field to filter on.

Scan stage changes the answer

Observed On spring-node, cdxgen 11.3.2 named 38 of the 40 shipped components from the source tree, 27 from the built artefact and 0 from the container image. syft 1.51.0 went the other way: 9, 33 and 33.

Likely reason At the source stage a tool can ask the build what it resolved, or read manifests without resolving them. In the artefact it has only the files that were packaged. In an image it first has to find the application among the operating system's files. Tools differ in which of these they do well.

What it costs No stage is best for every tool, so the stage is a decision to make and to record. An SBOM that does not say what was scanned cannot be compared with another.

Bundling conceals identity

Observed 4 components in these test cases are compiled into a JavaScript bundle during the build (lodash-es, lodash, react, react-dom). Tools named them in 21 of 31 attempts at the source stage, and in 0 of 32 at the artefact and image stages.

Likely reason After bundling, a library is bytes inside a file such as index-*.js. No manifest, lockfile or package directory survives for a tool to read, so there is nothing to recognise.

What it costs The library still ships and can still be vulnerable. An SBOM taken from the artefact or the image will not mention it; only one taken where the build can be seen will.

What the SBOM leaves out, nobody is warned about

Observed lodash@4.17.21 ships inside spring-node and has 2 published advisories. 6 of 8 SBOMs taken at the source stage raise them, and 0 of 8 taken from the artefact or the image. In the other direction, sbom-tool 4.1.13's source-stage SBOM for spring-node raises 10 advisories against components that are not in what ships.

Likely reason An advisory is found by looking up a component's identity. If the SBOM does not name the component, or names it under the wrong group, the lookup returns nothing. If it names something that never shipped, the lookup returns advisories that do not apply.

What it costs The first is a vulnerability nobody is told about. The second is work: someone has to investigate and dismiss every false alarm, and a team that learns to dismiss them will dismiss a real one.

Before you rely on this

Disclosure. The author of this benchmark also develops SBOM+ (sbom-plus-maven-plugin), one of the tools measured, and most of the test cases come from the same author's workshop on hidden dependencies. Read SBOM+'s results with that in mind. Every generated SBOM, the ground truth and the scoring code are in the repository, so any result can be checked. Maintainers of the tools measured here are invited to reproduce the run and to challenge a result or a test case by opening an issue.

The benchmark is small: 6 test cases covering Go, Maven, npm and pip. It measures how tools cope with specific hiding mechanisms, not how they do on a typical project, and it does not name a best tool. The limits are listed in full under Methodology. Everything is in the repository: the test cases, every generated SBOM, the scores and the code that produced them.
