The application and how it is built

A Spring Boot service with a React front end, shipped as one executable jar on a Temurin JRE image. It is a Maven multi-module build: a normalizer module, a service module, and a front end built by Vite whose output is copied into the jar as static files. Spring's BOM chooses the versions of most of the Java dependencies.

What gets hidden, and how

Three things happen to dependencies on the way in. commons-codec is shaded: its classes are relocated into normalizer's jar under another package name. lodash, react and react-dom are bundled into one JavaScript file. And versions such as jackson-databind's are decided by an imported BOM, not written in the service's POM.

Reading the result

Where a scanner reports the shaded commons-codec, it is reading a pom.properties file the shade plugin left behind, not the relocated classes. The workshop this case comes from shows the identification vanish when that one file is removed, so a match here does not mean the tool can see shaded code. The bundled libraries can be named from the lockfile at the source stage; after the build there is no package left to find. Test and dev dependencies outnumber what ships several times over, so how a tool treats scope decides whether its document describes the application or the whole project.

This is our interpretation. The counts above are what the run recorded; why a tool found or missed something is inferred from how the tool works, not established by the data. Limits of the benchmark.
