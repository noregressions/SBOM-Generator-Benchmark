The application and how it is built

A small Go command. Its go.mod requires four modules. The main package imports two of them, google/uuid and golang.org/x/text. A third, yaml.v3, is imported only by the tests. The fourth, jwt-go, is imported only by a file that is compiled when the build is given the debug tag, which the release build is not. The result is one static binary, shipped alone in an image built from scratch.

What gets hidden, and how

This case runs the other way from the rest: nothing is hidden from the dependency list, and the list says too much. go.mod must require every module any file in the module imports, under any build tag and in any test. The linker then includes only the packages the release build reaches. The Go toolchain also compiles its standard library into the binary, at its own version, and no dependency file mentions that.

Reading the result

A tool that reads go.mod reports what the module requires, and a tool that reads the binary reports what was linked; both are answering correctly, to different questions. The difference matters most for security. The unlinked modules here are old versions with published advisories, so an SBOM built from go.mod raises alarms about code that is not in the product, while one built from the binary does not. The standard library is the opposite risk: it is in every Go binary, and a source-stage SBOM usually cannot name the version that will be compiled in.

This is our interpretation. The counts above are what the run recorded; why a tool found or missed something is inferred from how the tool works, not established by the data. Limits of the benchmark.
