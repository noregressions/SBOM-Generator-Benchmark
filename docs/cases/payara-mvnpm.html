The application and how it is built

A Jakarta EE web application packaged as a WAR and deployed on a Payara server image. It has one ordinary Maven dependency, commons-lang3, which ships as a jar in WEB-INF/lib. Its browser code uses lodash-es, which arrives as a Maven artifact from mvnpm, declared as a dependency of the esbuild Maven plugin and not of the project. esbuild bundles it into assets/app.js. The Jakarta API is provided scope: needed to compile, supplied by the server, and absent from the WAR.

What gets hidden, and how

lodash-es is hidden twice. It enters through a plugin's dependencies, so it is never in the project's dependency graph. It is then bundled, so no package boundary survives in the WAR.

Reading the result

A tool that reads the project's dependency graph has no way to see lodash-es; a tool that lists what the build ran can name it at the source stage. The provided-scope API is the opposite case: it is in the graph and does not ship, so a tool that lists it without a scope overstates the WAR. In the image, the server's own libraries far outnumber the application's three components. Recall against so short a list says little about an image SBOM on its own.

This is our interpretation. The counts above are what the run recorded; why a tool found or missed something is inferred from how the tool works, not established by the data. Limits of the benchmark.
