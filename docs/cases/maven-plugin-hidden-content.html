The application and how it is built

A Java application that declares no dependencies at all. Its build runs a Maven plugin, trace-injector-maven-plugin, in the generate-sources phase. The plugin has a dependency of its own, trace-route-payload, which carries a route definition. The plugin turns that into a Java class and a ServiceLoader entry, and both are compiled into the application's jar.

What gets hidden, and how

Maven resolves a plugin and the plugin's dependencies into a classloader of their own, separate from the project's dependency graph. Code the plugin generates ends up in the jar as the application's own classes, with nothing to say where it came from.

Reading the result

The jar contains one package, the application itself, so a tool that names only that has described what ships. What it has not described is that part of the application's behaviour came from a plugin's dependency. That is a build-time influence, and an SBOM can record it only by listing what the build ran. Whether it should depends on what the SBOM is for. The benchmark counts such a listing as correct when it is marked as not shipping.

This is our interpretation. The counts above are what the run recorded; why a tool found or missed something is inferred from how the tool works, not established by the data. Limits of the benchmark.
