The application and how it is built

A .NET 6 console app with three old NuGet libraries: Newtonsoft.Json, log4net and SharpZipLib. The project file also references three System.* packages and a Roslyn analyzer. It's published self-contained, so the output folder holds the app, its libraries and the whole .NET 6 runtime, and the image adds nothing but the native libraries the runtime needs.

What gets hidden, and how

Two things are hidden, in opposite directions. Publishing self-contained copies the .NET runtime into the output from a NuGet runtime pack, Microsoft.NETCore.App.Runtime for the build machine's platform. No file in the source tree names it; only the publish output's deps.json does. Meanwhile restore resolves about 110 packages, mostly System.* and runtime.* packages pulled in by the old libraries, and publish drops nearly all of them because .NET 6 already contains newer copies. The analyzer runs inside the compiler and ships nothing.

Reading the result

Source-stage tools that read the restore graph report dozens of packages that never ship, including three with published advisories, and none of them can see the runtime. Artefact-stage tools that read deps.json see what ships, including the runtime, if they name it the way NuGet does. .NET 6 left support in November 2024, so the runtime in this artefact will never get another public fix; whether a scanner can say so depends on that one component being found and named.

This is our interpretation. The counts above are what the run recorded; why a tool found or missed something is inferred from how the tool works, not established by the data. Limits of the benchmark.
