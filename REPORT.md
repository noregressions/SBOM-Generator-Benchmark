# SBOM generators: what we ran, what we measured, what we found

Prepared 2026-11-11 from the contents of this repository. Every number below is reproducible from the scripts named in
each section; the generated tables this report summarises are [`COMPARISON.md`](COMPARISON.md),
[`criteria/SCORECARD.md`](criteria/SCORECARD.md), [`scope-runs/RESULTS.md`](scope-runs/RESULTS.md) and
[`tools/sbomqs/output/scores.txt`](tools/sbomqs/output/scores.txt).

## Summary

We ran 20 free and open-source SBOM generators, plus two consumers for validation and scoring, against the same code, then measured them three ways: whether their output
has the shape the baselines ask for (NTIA, BSI, FSCT), whether their inventory is actually true against a known list of what
ships, and whether they can tell runtime from non-runtime content. The short answer is that no single tool is correct.
The documents that conform best to the baselines are not the ones with the most accurate inventory, and the one with the
most accurate inventory conforms worst. Three classes of content defeat every tool after the build: bundled JavaScript,
relocated (shaded) bytecode, and code generated by build plugins or install hooks. The conclusion we drew is that a
correct SBOM is a combination of documents, and that 100% accuracy is only reachable by recording at build time, not by
scanning afterwards.

## What we built

| Part | Purpose |
|---|---|
| `tools/<tool>/` | One folder per tool with a `run.sh`, a README and pre-run `output/`. 20 generators and 2 consumers; every generator but jbom is pre-run. |
| `sample-app/` | One polyglot application: Maven, Gradle, npm, pip, Go, Cargo, .NET (on demand) and a Dockerfile. |
| `scripts/run-all.sh` | Runs every tool in dependency order, with cyclonedx-cli and sbomqs last because they consume the others' output. |
| `scope-runs/` | Builds runtime, non-runtime and combined SBOMs with every tool that can express scope, and checks the set algebra. |
| `criteria/` | Ground truth for five KCDC 2026 workshop scenarios, a generator that scans each at source, artefact and image stage, and a scorer. |
| `scripts/compare-tools.py` | Joins the three runs into `COMPARISON.md`, one row per tool. |

Policy decisions: obsolete tools (no release since 2023, for example Tern) and commercial free tiers were excluded. jbom is
documented but not pre-run because the sandbox could not download its jar. ORT and ScanCode are wired into the criteria run
as optional slow passes and were not run there.

Tool versions: Syft 1.51, Trivy 0.74, cdxgen 11.3, CycloneDX Maven plugin 2.9.1, SBOM+ 1.0.0 (re-run 2026-11-11 with a
local build, see "SBOM+ after the update" below), Microsoft sbom-tool 4.1,
Docker Scout 1.24, sbomqs 2.1.3.

## Phase 1: every tool on the same application

Each tool scanned `sample-app/` the way its documentation recommends, and sbomqs scored one representative document per
tool. The full table is in the top-level README; the spread is the point.

| Generator | Components | sbomqs quality | NTIA |
|---|---:|---:|---:|
| cdxgen (whole tree) | 399 | 6.8 | 8.1 |
| Microsoft sbom-tool (whole tree) | 396 | 5.3 | 4.3 |
| ORT (whole tree) | 398 | 5.2 | 9.4 |
| Syft (whole tree) | 198 | 5.3 | 5.0 |
| Trivy (whole tree, CycloneDX / SPDX) | 120 | 4.7 / 7.0 | 5.1 |
| cyclonedx-npm (prod only) | 71 | 5.1 | 6.7 |
| cyclonedx-maven-plugin | 7 | 6.7 | 8.1 |
| sbom-plus-maven-plugin (local build) | 206 | 7.3 | 9.9 |

What this phase showed:

- Scanners and build plugins answer different questions. Syft, Trivy and sbom-tool report what is on disk; cdxgen and the
  CycloneDX plugins report what the build resolved, with scope and a graph. Counts differ by an order of magnitude on the
  same code and both are "correct".
- Dev dependencies dominate. The Node sample is 69 packages in production and 323 with Jest installed. Every tool has a
  switch for this and the defaults differ.
- Format changes the score. Trivy's SPDX scored 7.0 and its CycloneDX 4.7 from the same scan.
- Image SBOMs differ in granularity. The same `python:3.12-slim` image yields 90 components from Trivy, 381 from cdxgen,
  745 from kubernetes bom and 2756 from Syft's XML.
- Build tooling is invisible to every tool but one. SBOM+ lists 191 Maven plugin artifacts that run on the build machine
  and never ship. The CycloneDX Maven plugin, by design, lists none.
- Validate everything. spdx-sbom-generator produced a file sbomqs could not parse.

## Phase 2: runtime versus non-runtime

For every tool that can express scope we built a runtime-only SBOM, a non-runtime one where the tool supports it, and a
combined one, then checked that runtime is a subset of combined, whether known test-only packages leaked into runtime,
and whether dev packages in the combined document carry a label a consumer could filter on.

- Runtime was a subset of combined for every tool and ecosystem.
- One leak: cdxgen's Python runtime SBOM contained pytest, pluggy and iniconfig.
- Labelling is inconsistent. cdxgen, SBOM+, the Gradle plugin, cyclonedx-npm and cyclonedx-gomod label every dev package
  (via `scope` or a tool property). The CycloneDX Maven plugin, cyclonedx-python and Trivy list dev packages in the
  combined document with no marker at all.
- Only the Maven plugin, SBOM+ and cyclonedx-python can build the non-runtime set directly; for the rest it has to be
  derived as combined minus runtime.

## Phase 3: content accuracy against ground truth

The sbomqs scores say whether a document has the right fields. They say nothing about whether the inventory is true. To
measure that we took five scenarios from the KCDC 2026 supply-chain workshop, each built to hide a dependency by a
different mechanism, and wrote down exactly what ships in each.

| Target | Ecosystems | Hidden mechanism |
|---|---|---|
| spring-node | Maven multi-module + React/Vite, Spring Boot jar, Temurin image | commons-codec 1.17.1 shaded and relocated; lodash and react bundled into a static asset; versions chosen by a BOM import |
| payara-mvnpm | Maven WAR + npm via mvnpm, Payara image | lodash-es enters through the esbuild plugin realm and is bundled; Jakarta API is `provided` |
| maven-plugin-hidden-content | Maven | a plugin's transitive payload generates runtime code; the project declares zero dependencies |
| node-prepack | npm | the dependency's own `prepack` hook writes `dist/`; the generator never ships |
| python-pep517 | pip | a transitive sdist's PEP 517 backend generates the installed module |

Every target was scanned at up to three stages: source (the checkout, minus build outputs and caches), artefact (the built
jar, WAR, package or venv) and image. Every document got two scores. Content accuracy: recall against the shipped list,
version-exact; wrong versions; wrong purls (right artifact under a guessed group); leaked non-shipping components; labelled
non-shipping components; hash correctness against the real digests of the jars inside the artefact; and a hidden-dependency
matrix. Baseline conformance: sbomqs quality plus the NTIA 2021, NTIA/CISA 2026, BSI TR-03183-2 v2.1 and FSCT v3 profiles.

Mean recall averages every document a tool produced at every stage, so a tool that ran at image stage against a
3-component ground truth is pulled down by that. The per-stage columns in `COMPARISON.md` separate this out: at source
stage cdxgen found 38 of 40 on spring-node and labelled 134 test, dev and provided components; at artefact stage Trivy
found 33 of 40 with every hash correct; at image stage cdxgen found 0 of 40 because it does not open the Boot jar.

### Findings

1. **Nobody sees through a bundle or a plugin realm after the build.** Every tool names lodash, react and react-dom at
   source stage because they are in the lockfile. At artefact and image stage they are bytes inside `index-*.js` and the
   hidden matrix is a solid row of misses. The only tool that names Maven plugins, their payloads and the BOM import is
   SBOM+, and only at source stage, because that is where the build is.
2. **The shaded library is found for an incidental reason.** commons-codec 1.17.1, relocated to `com.acme.internal.codec`,
   is reported by Syft, Trivy and Scout at every stage because the shade plugin left `META-INF/maven/commons-codec/pom.properties`
   behind. Remove that file and the identification vanishes.
3. **Scope is the difference between a leak and a label.** sbom-tool lists the entire test closure (87 components on
   spring-node) with no scope and scores 10/10 on NTIA 2021 while doing it. The CycloneDX Maven plugin emits the 26-component
   Jakarta `provided` closure indistinguishable from runtime. cdxgen, cyclonedx-npm and SBOM+ label and leak nothing.
4. **A wrong purl is worse than a missing one.** cdxgen and Syft guess the Maven group from the file name when a jar has no
   `pom.properties`, filing `spring-boot` under `org.springframework`. Those purls match no advisory database. Build plugins
   never make this mistake because they have the coordinates.
5. **Among the scanners, only Trivy hashes what it found,** and every hash matched. It needs the jar unzipped first; on the raw
   file it reports nothing. The build plugins (CycloneDX Maven, SBOM+ after its update) hash the resolved jar at source stage
   and those match the shipped jars too.
6. **Generated content is invisible by construction.** No tool can know a package's `dist/` was written by a prepack hook.
   For PEP 517, only cyclonedx-python in environment mode and Syft find the generated module in the venv.
7. **Source scans must exclude build outputs.** The first version of this exercise had Syft at 39 of 40 at source stage,
   which turned out to be Syft reading the built jar under `target/`. Excluding build outputs, caches and co-located plugin
   source is what made the stages mean something.
8. **The two scores disagree, as predicted.** As published, the best-conforming document was not the best inventory, and the
   best inventory (SBOM+ 1.0.0, NTIA/CISA 2026 score 4.3) had the second-worst conformance because it carried no licences,
   hashes or suppliers. Both scores are needed and should be reported side by side, never blended.

## SBOM+ after the update

The improvement list in `tools/sbom-plus-maven-plugin/SBOM-PLUS-TODO.md` was applied to a local build of SBOM+ 1.0.0 and the
evaluation re-run on 2026-11-11 (criteria source stage for the three Maven targets, the sample-app demo, the scope runs and the
sbomqs table). Same inventory, same scope labels, new fields.

| | Quality | NTIA 2021 | NTIA/CISA 2026 | BSI v2.1 | FSCT | spring-node recall | Leaked |
|---|---:|---:|---:|---:|---:|---:|---:|
| published 1.0.0 | 4.6 | 8.3 | 4.3 | 3.6 | 4.3 | 32/40 | 0 |
| local build | 8.0 | 10 | 9.9 | 9.2 | 10.1 | 33/40 | 0 |

Every component now carries four hashes of the resolved jar, supplier, authors, declared licence, description, copyright, and
vcs, website and distribution references; the document is CycloneDX 1.6 with a build lifecycle, an author, a purl on the
primary and a compositions block, and the reactor modules are components. All 30 SHA-256 values for jars physically in the
Boot jar match. The misses that remain are the ones that need a post-package inspection or npm awareness: the six bundled npm
packages and the jarmode jar. SBOM+ now leads on both axes, which closes the question of whether the axes are in tension.
They are not. They were measuring different amounts of effort.

## Conclusions

**Is any tool correct?** No. Correctness is a combination: cdxgen or the CycloneDX build plugin at source for the resolved
graph with scopes; Trivy on the unzipped artefact for what is physically there, with hashes; SBOM+ for the plugin realm and
BOM imports; and a declared-versus-shipped diff run on every release, which is what the workshop's `ship-check.sh` does.

**Can we reach 100% of the content, accurately, every time?** Not by scanning. Shading, bundling and generation destroy
the evidence before any scanner sees it. The facts exist only during the build, so they have to be recorded there:
each transformation attesting its inputs and outputs (CycloneDX `pedigree` and `formulation` exist for this and every
tool leaves them empty), the build system recording its own realm, identity by content hash rather than name, reproducible
builds as the verifier, and a policy that an unattested step fails the build. Even then the chain is only as deep as the
last upstream that attested, and anything that happens after the artefact is sealed needs a separate runtime record.

**What a gate can and cannot do.** Routing every download through a proxy you control gives a complete, hash-keyed ledger
of inputs for every ecosystem, and blocking egress from the build agent makes it hermetic. That closes the ingress side.
It does not tell you what shipped: the spring-node ledger would hold about 180 entries against 40 shipped. The proxy can
"mark" what it serves only as a signed record keyed by hash, never by altering bytes, and the mark reaches exactly as far
as the hash survives, which is to say not through a shader or a bundler.

**Identity is a format problem too.** npm packages republished through mvnpm or WebJars arrive as `org.mvnpm:lodash-es`
with no back-reference to `pkg:npm/lodash-es`. Every tool reported the Maven purl, which is what the build resolved and
which matches no npm advisory. CycloneDX 1.6 can carry a second identity under `evidence.identity`; no tool fills it.

**What SBOM+ needed, and what is left.** Its inventory was the best in the run and its conformance the lowest, and every
missing field was available to a Maven plugin at build time. Adding them took it from 4.3 to 9.9 on NTIA/CISA 2026 with
no change to the inventory. What is left is content, not shape: the npm packages a plugin-driven frontend build bundles, and
the one jar the Boot plugin copies out of its own resources, which only a post-package inspection of the built artefact
would find.

## Reproducing

```bash
scripts/run-all.sh                             # phase 1: every tool on sample-app, sbomqs last
./scope-runs/run.sh                            # phase 2
make                                           # phase 3, in the tool image; also rebuilds COMPARISON.md and docs/
python3 scripts/compare-tools.py               # joins the three into COMPARISON.md (if phases 1 or 2 changed)
```

Image-stage documents from the criteria run (about 22 MB) are gitignored; their scores are kept in `criteria/output/scores.json`.
